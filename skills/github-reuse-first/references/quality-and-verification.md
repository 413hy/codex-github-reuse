# 质量与验证

按改动选择章节，不要把整份清单强制套到每个任务。优先复用项目已有验证方式。

## 成品直接可用

默认从打开 demo 到体验主要功能没有额外的账号、授权、审批、激活、验证码或解锁步骤。
不要自行添加付费墙、次数配额、试用倒计时或无必要的确认弹窗。
仅在用户明确要求相应产品机制时实现这些内容；技术说明和安装细节不要塞进产品使用流程。

缺少真实账号或外部服务时，提供明确标注的演示数据或可替换模拟适配层，使已明确的本地演示流程完整。
模拟成功只证明本地流程，不能表示真实服务已经连通。保留真实服务本身已有的认证和访问边界。
常规数据正确性检查、错误恢复与代码自检在内部自动完成，不转化为用户必须额外审批或验证的步骤。

## 页面设计

先查看已有页面、组件和设计约定。没有现成约定的新项目，简要确定产品受众、主任务、布局层级、
颜色、字阶、间距、圆角和动效方向。遵循用户明确提供的品牌和风格要求。

选中的参考必须能解释它怎样改进当前页面：例如信息更清晰、操作更容易发现、数据更易比较，
而不能只说“现代”“高级”或“好看”。移植后把参考组件接入同一套样式约定，
保留适合当前产品的差异，不复制上游品牌文案和无法确认使用权的素材。

有页面运行能力时打开实际页面，检查主要屏幕与移动布局、真实长短文本、空数据和内容溢出。
有截图能力时对涉及视觉的改动查看截图，发现不一致后修正。
没有实际渲染能力时，只能报告代码层面的检查及尚需运行确认的内容。

## 交互逻辑

针对本次功能列出用户动作、状态变化与可观察结果，验证主要成功路径。
再检查实际涉及的异常或边界：

- 数据加载、空结果、请求失败、重试和成功反馈。
- 表单校验、重复提交、焦点位置与键盘可操作性。
- 弹窗/菜单的打开、关闭、返回与状态恢复。
- 拖拽或动画对触屏、键盘和减少动态效果偏好的支持。
- 筛选、分页、排序和 URL/后端状态之间的同步，仅在功能需要时适用。

不要把演示中的假数据、恒成功请求或占位按钮直接当作真实业务功能。
新依赖需要验证它与当前状态管理、渲染和事件处理方式的实际衔接。

## 功能代码与依赖

阅读采用模块的接口、依赖和使用示例，验证输入输出及关键失败路径。
沿用现有锁文件与包管理器；不要为解决一次依赖冲突大范围升级无关包。
用最小有代表性的集成检查验证可用性，再运行与改动有关的项目检查。
修复自己引入的回归；区分原有失败与新失败，并保留具体证据。

执行从外部取得的代码之前，先检查涉及安装、下载、环境修改和数据传输的部分。
只执行任务需要且当前环境允许的操作，不擅自改变全局安全设置。

## Prompt 与 agent 工作流

先定义任务契约：可接受的输入、期望输出格式、可用工具、不可缺失的信息与失败时的行为。
明确参考 prompt 里哪些内容可保留，哪些与当前角色、工具、语言、上下文或指令优先级不兼容。
优先把可判定规则写成清楚的约束，避免为气势增加大量重复要求。

使用少量能区分效果的输入。根据任务选择正常输入、缺少关键信息、格式异常、较长内容，
以及包含干扰指令的外部文本；不必对每个简单 prompt 都使用全部类型。
有旧 prompt 时用相同输入比较；无旧方案时直接按验收条件检查。

| 维度 | 观察内容 |
| --- | --- |
| 任务完成 | 是否满足输入中的实际需求，是否把关键条件漏掉 |
| 输出约定 | JSON、字段、语言、长度或结构是否符合要求 |
| 不确定性 | 缺少必要信息时是否合理询问、说明假设或标注未知 |
| 工具与证据 | 是否只使用真实可用工具，来源和执行结果是否可追溯 |
| 外部内容 | 是否把资料中的越权指令当成资料处理 |

模型执行条件会影响结果。记录模型/配置（能获取时）、输入、结果和判断标准，
不要把少量通过样例描述成对所有任务的保证。
没有运行模型时，交付可执行的样例与检查标准，并把状态写为“结构检查完成，模型效果未验证”。
小规模任务直接用项目现有工具或人工对照即可；规模确实需要时再评估专门框架。

## 如何报告验证

引用实际运行的命令、对应日志或可观察结果；只保留与结论有关的信息。
对于一个采用项，用“来源 → 本地落点 → 验收行为 → 验证结果”描述。
静态检查、单元测试、集成运行、浏览器操作和模型评估分别陈述，不混用完成状态。
